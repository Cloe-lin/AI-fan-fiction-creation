# AI 产品经理共性能力 × 本项目对照

> **共识：** 不同行业/岗位的 AIPM 工作内容不同；下列 5 项是**跨行业必须掌握的共性能力**。行业差异（电商/内容/金融/工具等）可在入职后「干中学」。

---

## 共性能力总表

| # | 共性能力 | 重要度 | 一句话 |
|---|----------|--------|--------|
| 1 | 会写 Prompt，并能根据用户反馈数据优化/迭代 | ★★★★★ | Prompt 是 AIPM 的「需求文档+策略开关」 |
| 2 | 构建评测标准 + 评测集 | ★★★★★ | 没有评测就没有迭代，只有玄学调参 |
| 3 | Vibe coding：策略评审前自己跑通 Demo | ★★★★ | 用可运行原型对齐认知，降低空对空评审 |
| 4 | 判断：什么用 AI，什么用工程即可 | ★★★★★ | 避免「凡事先上模型」的成本与风险 |
| 5 | 懂 Agent、RAG 底层逻辑，并会落到业务 | ★★★★ | 能选型、能拆链路、能和研发共语言 |

## 能力 1：Prompt 编写与基于反馈的迭代

### 能力要求（共性）

- 能把业务目标拆成系统提示 / 用户提示 / 输出格式约束  
- 能根据badcase、用户反馈、日志做小步迭代（改约束、加 few-shot、调拒绝规则）  
- 知道 Prompt 变更要版本化，并和评测结果绑定  

### 在本项目中的体现（面试怎么说）

| 业务点 | Prompt / 策略位置 | 你可强调的产品动作 |
|--------|-------------------|-------------------|
| 创作 | 系统人设 + 档案注入 + 结局硬约束 + 用户剧情 | 把「别 OOC」从用户口头提醒，升级成系统 Prompt 结构 |
| 审查 | 原著专家视角、问题类型枚举、JSON 输出 | 用结构化输出方便前端展示与自动修订决策 |
| 修订 | 问题清单 + 原稿 + 档案再生成 | 低分闭环，而不是一次性碰运气 |
| 深档抽取 | 字段约束（字符串/列表）、深/简长度不同 | 用格式约束降低解析失败与脏数据 |

**迭代话术（即使数据还少也要会说）：**  
「上线后我会建 badcase 池：OOC、结局矛盾、中间篇补白、偏离用户走向。每周用评测集回归 Prompt；改动必须带来审查均分↑或修订触发率↓，否则回滚。」

### 差距与补强

- 现行：策略已产品化进链路，但**缺少正式 Prompt 版本表 + 反馈→改 Prompt 的运营节奏**  
- 补强：准备 1 页「Prompt 变更单」模板（背景/改动/评测对比/结论）

## 能力 2：评测标准与评测集

### 能力要求（共性）

- 定义「什么叫好」：维度、量表、通过线  
- 建评测集：黄金集（稳定回归）+ 挑战集（边界/攻击）+ 线上抽样  
- 能区分自动指标与人工抽检，避免只看手动体感  

### 在本项目中的体现

**已有雏形（可包装成评测体系）：**

| 维度 | 现行机制 | 产品化评测标准建议 |
|------|----------|-------------------|
| 人物一致性 | 审查分 0–100，阈值 60 | 均分、&lt;60 占比、OOC 类 issue 占比 |
| 结局合规 | 审查项「结局矛盾 / 中间篇补白」 | 中间篇补白率必须≈0 |
| 用户意图 | direction_mismatch | 偏离用户设定的比例 |
| 连载连贯 | 续写记忆注入 | 人工抽检「是否接上章结尾」 |
| 供给质量 | 准备成功/失败 | 准备成功率、P50 耗时 |

**评测集怎么建（面试必答）：**

1. **黄金集（20～50 条）：** 固定书目 + 固定人物 + 固定剧情设定，每次改 Prompt/模型都跑  
2. **挑战集：** 易 OOC 人物、强冲突关系、刻意诱导写中间篇的 prompt  
3. **线上集：** 真实用户设定抽样，周更  

### 差距与补强

- 现行：有在线审查，但**还不是离线可回归的评测集**  
- 补强：先做 20 条黄金集表格（输入/期望约束/禁止项），作为 AIPM 作品集附件

## 能力 3：Vibe coding（评审前自己跑通 Demo）

### 能力要求（共性）

- 不要求成为工程师，但能用 Cursor/低代码把链路跑通  
- 策略评审带的是「可点的 Demo + badcase」，不是纯 PPT  
- 能独立验证：API Key、主路径、明显失败点  

### 在本项目中的体现

本仓库本身就是 **可运行 Demo**：

- 本地：`uvicorn` + `http://127.0.0.1:8010/`  
- 可演示：登录 → 选书/上传 → 生成 → 看评分 → 续写  
- 可演示失败与边界：未登录、他人存档 403、准备失败重试  

**面试话术：**  
「策略评审前我会自己跑通主路径，带着生成样例和审查报告进会，用事实对齐『深档是否有用、阈值是否合理』，而不是空谈要不要上 Agent。」

### 差距与补强

- 继续保持：任何新策略（改审查阈值、改深档字段）先本地 A/B 几条再提评审  
- 加分：录 1～2 分钟 Demo 视频放作品集

## 能力 4：什么用 AI，什么用工程解决

### 能力要求（共性）

- AI 适合：语义理解、生成、模糊匹配、需要泛化的判断  
- 工程适合：权限、计量、确定规则、缓存、限流、结构化存储、工作流状态机  
- 能算成本/延迟/可解释性，避免「全能 Agent」幻觉  

### 在本项目中的划分（这是高分回答）

| 问题 | 用 AI？ | 用工程？ | 原因 |
|------|---------|----------|------|
| 人物会不会 OOC | ✅ 审查模型 | ✅ 深档注入结构 | AI 判，工程管输入约束 |
| 只写结局后、禁止中间篇 | ✅ 审查辅助 | ✅ 硬规则写进系统 Prompt + 产品文案 | 规则可工程化，审查兜底 |
| 用户互不可见存档 | ❌ | ✅ owner_id + 鉴权 | 确定性安全问题，禁止靠模型「自觉」 |
| 公私书库可见性 | ❌ | ✅ visibility / owner | 同上 |
| 候选人物抽取、深档生成 | ✅ | ✅ 异步任务/进度/重试 | AI 生产内容，工程管可靠交付 |
| 登录注册 | ❌ | ✅ JWT / 预置账号 | 身份是工程问题 |
| 原著相关片段 | ✅ Embedding+检索 | ✅ 分块入库、按书隔离 collection | 经典 RAG：模型负责表示，工程负责索引与隔离 |
| 按钮样式/粉金主题 | ❌ | ✅ 前端 | 无智能需求 |

**金句：**  
「权限、隔离、计费、状态机用工程；语义与生成用 AI。本项目里最贵的 AI 用在『写』和『审』，最不能错的『谁能看』全走工程。」

## 能力 5：Agent / RAG 底层逻辑与业务用法

### RAG（本项目已落地，必须讲透）

**底层逻辑（三句话）：**  
1. 把文档切块并向量化入库  
2. 用用户问题（剧情设定等）检索相似块  
3. 把检索结果塞进 Prompt，让生成「有据可依」

**业务用法（本项目）：**  
- 按**小说隔离**索引，防止串设定  
- 创作时检索原著片段并在前端展示，提升信任  
- 与「结局记忆」配合：RAG 补细节，结局摘要管大方向  

**边界：** RAG 不能替代版权合规；检索差时会「一本正经引用错段」——要用评测集盯引用相关度。

### Agent（本项目偏工作流，面试要会对比）

**底层逻辑（三句话）：**  
1. 模型不只生成文本，还能规划步骤、选工具、观察结果再行动  
2. 典型循环：思考 → 调用工具 → 观察 → 再思考  
3. 成本高、不稳定，适合任务目标清晰且工具可靠的场景  

**本项目为何没上「全能 Agent」：**  
现行是 **编排好的 Pipeline（工作流）**：准备流水线、创作→审查→修订，步骤由产品/工程固定，而不是让模型自己决定下一步。  

**面试加分：**  
「准备环节未来可局部 Agent 化（如自动选深档人物），但权限与入库必须工具化、可审计；创作主链路继续用可控工作流，避免 Agent 乱调工具产生不可控费用。」

## 用本项目讲「我具备 AIPM 共性能力」的 60 秒整合稿

> 我认为 AIPM 共性能力就五块：Prompt 迭代、评测、能跑 Demo、AI/工程边界、RAG/Agent 素养。  
> 在同人文项目里：我把人设与结局做成结构化 Prompt 策略；用审查分和 issue 类型当评测雏形，并清楚下一步要建黄金集回归；策略会前我自己跑通上传和连载 Demo；权限隔离等确定性问题坚持工程解决，只把生成与质检交给模型；RAG 已按书隔离落地，Agent 则克制使用，主链路用可控工作流。  
> 行业玩法可以入职后学，但这五块是我已经在项目里练过的。

## 建议你补的最小作品集（针对能力 1、2）

1. **Prompt 变更单 × 2 次**（改审查提示前后对比 5 条样例）  
2. **黄金评测集 20 条**（Excel：输入设定 / 必须满足 / 禁止项 / 人工分）  
3. **AI vs 工程决策表**（可直接用本文表格）  

做完这三样，共性能力在面试里会非常「可被追问、可被验证」。
